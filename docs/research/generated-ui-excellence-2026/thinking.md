# Thinking Log — Generated UI Excellence 2026

Raw reasoning, hypotheses, surprises, dead ends, and revised conclusions.

---

## Initial Framing

The question is: what does "beyond world-class" mean for a DSL compiler that emits self-contained Flask apps as inline HTML/CSS/JS strings, with no build step and no npm?

The key constraint — **no build step, no npm, self-contained** — is actually an advantage for some performance metrics. No hydration cost. No bundle parsing. No critical path network waterfall from JS chunks. A server-rendered HTML page that arrives complete is intrinsically faster-to-interactive than a SPA that must fetch, parse, and execute JS before rendering anything meaningful.

The constraint is a disadvantage for: rich component libraries (Radix, shadcn), reactive state management, incremental updates without page reloads.

So the research question becomes: **given the architecture, what is the highest achievable bar on accessibility, performance, and resilience — and what does it look like in terms of generated HTML strings?**

## Phase 1: Accessibility Research

### Starting hypothesis
Most generated UIs fail the same handful of things: missing labels, bad contrast, missing alt text, no skip links, no landmarks. These are "the basics." I expected the research to confirm this and give me WCAG 2.2-specific additions.

### Confirmed: the six universal failures
The WebAIM Million 2026 data is sobering. 95.9% of pages fail. The six categories are unchanged for seven years. This means:

1. Generated HTML that emits correct labels, alt text, landmark structure, and reasonable contrast **already beats 95% of the web by default.** The bar is low. Meeting it requires discipline in the generator, not rocket science.

2. The failure mode for generated UI is different from hand-written UI: in hand-written HTML, developers forget. In generated HTML, the generator pattern is wrong once and wrong everywhere. This is both the risk (systematic failures) and the opportunity (systematic fixes).

### Surprise: ARIA makes things worse on average
Pages with ARIA average 59.1 errors vs 42 without ARIA. This is not because ARIA is bad — it's because ARIA is misused. Developers add `role="button"` to a `<div>` without keyboard handling, or add `aria-label` that conflicts with visible text, or nest ARIA roles incorrectly.

Implication for APG generator: **emit ARIA only when the semantic is correct and complete.** A `<button>` element with visible text needs no ARIA. A `<div>` acting as a button needs `role="button" tabindex="0"` AND keyboard event handling AND correct label. If the generator can't guarantee the complete pattern, use native HTML elements instead.

### WCAG 2.2 new criteria — what's actually hard for generated UI

Went through all 9 new SC:

- **2.4.11 Focus Not Obscured (AA)**: This one is subtle. Sticky headers in generated dashboards (common pattern) will obscure focused form fields. The generator needs to emit `scroll-padding-top` equal to the sticky header height, so that when an element is scrolled into view for focus, the header doesn't cover it.

- **2.5.8 Target Size (AA)**: The 24×24px minimum is easy for primary buttons. It's a trap for: icon-only action buttons in table rows, pagination dots, kanban card drag handles, close buttons on badges. Every generated icon-only interactive element needs explicit sizing check.

- **2.5.7 Dragging Movements (AA)**: Kanban boards are central to APG. Drag-drop without keyboard alternative is an AA failure. The "Move" button + menu pattern (Salesforce UX reference) is the clean solution — it provides a complete alternative and also improves usability for touch-only devices.

- **3.3.7 Redundant Entry (A)**: Multi-step wizard flows that re-ask fields already completed. The generator knows what fields exist across wizard steps — it should be able to pre-fill step 2 with step 1 data automatically.

- **3.3.8 Accessible Authentication (AA)**: Generated login pages with CAPTCHA fail this. Rate-limiting + magic links is the compliant alternative. This is an architectural constraint on generated auth flows, not just a CSS fix.

- **3.2.6 Consistent Help (A)**: Help mechanisms must appear in the same position across pages. If the generator emits a help button in the nav on one page, it must be in the nav on all pages. Consistency is free when the layout is generated by template.

### What I didn't expect to find: EU Accessibility Act enforcement

The EAA went into effect June 2025, requiring WCAG 2.1 AA for digital products/services in the EU. WCAG 2.2 AA is a superset, so compliance with 2.2 AA satisfies EAA. This means accessibility compliance now has legal/commercial weight beyond reputation.

## Phase 2: Static HTML Checks

### Starting hypothesis
I expected there to be robust Python-based tools for checking generated HTML templates. curlylint seemed promising.

### Reality check: curlylint is unmaintained
curlylint's last significant GitHub activity was 2023. It's a useful reference for what checks are possible, but relying on it for a CI pipeline is risky. The 7 rules it provides are implementable directly with regex + HTMLParser in Python.

### The better pattern: own your checks
Since APG generates the HTML (it doesn't receive arbitrary HTML), the generator already knows the semantic intent of every element. A `<button>` generated for a "delete" action knows its purpose. The static checks should be:

1. **In-generator assertions**: Before emitting HTML, assert that every field-generating call includes a label. This is a compile-time check, not a post-hoc lint.

2. **Output validation**: Run checks on the generated HTML string before returning it. This catches any gaps from template composition.

3. **CI test suite**: Render each page type and run the full check battery.

The heading hierarchy checker and form label checker written in pure Python in the README are directly implementable. No external dependencies needed.

### html-validate vs curlylint
html-validate (Node) is the strongest static checker. It was described as "second overall after the W3C v.Nu HTML checker" and "best among the fast linters." Worth adding to CI even though it's Node — it can run on generated HTML files as a post-build check.

## Phase 3: Core Web Vitals

### Starting hypothesis
For server-rendered HTML with inline CSS/JS, the main threats are: large CSS, JavaScript blocking render, and layout shift from dynamic content.

### Confirmed: inline CSS is the right call
Since APG already inlines CSS in `<style>` blocks, it naturally avoids the render-blocking `<link rel="stylesheet">` issue. This is a genuine advantage over frameworks that rely on external stylesheets.

### LCP for generated pages
The LCP element is almost always the `<h1>` or first large text block in server-rendered pages without images. This makes LCP optimization simple: ensure the `<h1>` is in the first screenful and is styled immediately (not pending a font load).

System fonts are the correct call for generated admin UI. They eliminate the entire class of font-related LCP and CLS issues. Any generated UI that uses Google Fonts has an unnecessary network dependency and LCP risk.

### CLS is the sneaky one
content-visibility: auto is excellent for long pages but introduces CLS if not paired with contain-intrinsic-size. Found the specific community discussion confirming this. The fix is straightforward but must be implemented by default — generated long-page sections should always include both properties.

Image dimensions are easy to enforce in a generator: every `<img>` call must include width/height. This is a generator contract, not a developer responsibility.

### INP for vanilla JS
This was the most technically interesting research area. INP measures every interaction, not just first interaction. For generated admin UIs with large tables (hundreds of rows), sorting/filtering handlers can easily exceed 50ms and hurt INP.

Key insight: **event delegation at the container level** is both an a11y pattern (single listener, roving tabindex) and a performance pattern (fewer listeners, less memory, better INP). The two concerns reinforce each other.

The scheduler.yield() pattern is clean but has Firefox support issues. The setTimeout(0) polyfill is safe everywhere.

## Phase 4: Resilience UX

### offline detection
navigator.onLine = false is reliable. navigator.onLine = true is not. This asymmetry is important: you can confidently show "you are offline" when onLine is false, but you shouldn't assume connectivity when it's true. The HEAD fetch verification is the right approach for critical operations.

Mobile caveat: background tabs on iOS/Android get killed without firing beforeunload. This means the beforeunload → sendBeacon draft-save pattern is unreliable on mobile. For forms with critical data, periodic autosave (debounced) is more reliable than relying on unload events.

### Form draft persistence: what not to store
Never store password, token, cvv, secret fields. This should be explicit in the generator — any field with type="password" is automatically excluded from draft persistence.

The 7-day expiry on drafts is an important UX detail. A draft that restores a form you submitted 3 weeks ago is confusing. Shorter expiry (24-48 hours) is often more appropriate for admin workflows.

### Error boundaries: the vanilla JS story is weak
React's error boundaries are elegant. The vanilla JS equivalent (window.onerror + unhandledrejection) is coarser — it catches uncaught errors, not component-level render errors. The practical implication: generated JS should be defensive. Every fetch callback needs explicit error handling. Every DOM manipulation should check if the element exists before operating on it.

The global handlers are a safety net, not a primary strategy.

### Optimistic UI: when NOT to use it
The research makes a clear distinction: use optimistic updates for low-stakes reversible actions (status changes, bookmarks, soft deletes), not for financial transactions, hard deletes, or payment operations. Generated admin UI needs to know which actions are which — this is a semantic property of the capability schema, not something determinable at render time.

## Phase 5: Competitive Analysis

### Django admin — adequate, not aspirational
The 2024 blog post revealed that Django admin scores 80.5/100 on accessibility vs industry average. The team knows the gaps (Windows High Contrast, component gaps) and is working on them, but the current state is below average for the industry. APG should target significantly higher.

The specific wins from Django 5.0 (help text associated with inputs, error messages programmatically associated) are baseline requirements — they should be in APG's generated HTML from the start, not retrofitted years later.

### shadcn/ui — the reference bar for component quality
The 2026 audit finding that 34/48 components pass WCAG 2.2 AA out of the box is illuminating. Even the best-regarded component library has ~10% with significant gaps and ~19% needing fixes.

The specific failures are instructive:
- Focus ring contrast failure (ring-1 ring-ring/50 is too subtle)
- Charts with no accessible alternative
- Combobox missing ARIA attributes
- Data table missing caption and sort announcements

These are exactly the patterns APG generates. The lesson: don't assume that "correct structure" is sufficient — each widget type needs an explicit ARIA completeness audit.

### Rails/Phoenix — same architecture, but no guarantees
Both Rails (Hotwire) and Phoenix (LiveView) use server-rendered HTML with progressive enhancement. Neither enforces accessibility by default. The developer is responsible for adding ARIA. The generator that enforces ARIA automatically has an architectural advantage over these frameworks.

The Phoenix LiveView focus-preservation on DOM morphing (maintaining keyboard focus when only parts of the page update) is a strong UX feature. Generated HTMX or plain fetch patterns in APG should do the same: after partial page updates, preserve or intelligently redirect focus.

---

## Key Revised Conclusions

1. **The bar for "beating world-class" is surprisingly low in absolute terms.** 95.9% of sites fail. Meeting WCAG 2.2 AA puts generated UI in the top 4%.

2. **The generator is a force multiplier.** A correct ARIA pattern in the generator template means every generated page gets it right. Django spent years retrofitting this. APG can have it from day one.

3. **System fonts + inline CSS + defer JS is a complete performance stack** for no-build-step HTML. No exotic techniques required. The architecture inherently avoids the biggest LCP risks.

4. **Resilience patterns need explicit generator support.** Offline banners, error fallback elements, and draft persistence hooks should be emitted by default in the page shell, not left to per-page customization.

5. **The ARIA-makes-things-worse finding is a warning.** Every ARIA attribute emitted must be complete and correct. Half-implemented ARIA (role without keyboard handling, aria-label without corresponding structure) is actively harmful.

6. **Open question worth investigating further**: focus management after server-rendered fragment updates (HTMX `hx-target` swaps, fetch+innerHTML). The page updates but keyboard focus stays on the triggering element — this is usually correct, but for list filtering where the triggering element disappears, focus management needs explicit code.
